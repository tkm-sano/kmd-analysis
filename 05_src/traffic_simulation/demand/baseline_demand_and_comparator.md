# 大田区の共通需要計算と未最適化基準

## 1. 目的と位置付け

この文書は、大田区について未最適化基準、古典最適化、Qiskit Aer QAOAへ共通に与える合成需要と、未最適化基準の比較器を固定する正本である。公開統計から実顧客、実注文、実配送先、実配送停止回数または実配送順序を復元したとは扱わない。

未最適化基準は実在事業者の現行運用を表すものではなく、同じ配送問題に対して訪問順序を最適化しない`fixed_hash_no_reordering`比較器とする。古典最適化とQAOAの改善量は、この明示的な帰無比較器との差として解釈する。

## 3. 公開統計から計算する値

### 3.1 2024年推定メッシュ人口

500mメッシュ`m`の2020年人口を`n_m^(2020)`とする。N03大田区境界と交差するメッシュでは、面積按分を行う場合の暫定人口を次とする。

```text
w_m = n_m^(2020) * area(mesh_m intersection ota_boundary) / area(mesh_m)
```

2024年4月1日の大田区人口総数`N_ota = 736652`へ比例調整する。

```text
N_m_expected = N_ota * w_m / sum_m(w_m)
```

整数`N_m`は最大剰余法で配分し、次を必須条件とする。

```text
sum_m(N_m) = 736652
N_m >= 0
```

同率時は`KEY_CODE`昇順とする。これは2020年のメッシュ内人口分布が2024年まで比例的に維持されたという推定であり、2024年の500mメッシュ観測人口ではない。面積按分は境界メッシュ内で人口が一様という仮定を含むため、按分前人口、交差面積率、按分後値を保存する。

### 3.2 全国宅配便取扱個数の人口換算原単位

```text
q_base = 5,031,470,000 / 123,802,000 / 365
       = 0.111345933951539499... 宅配便個数相当／人・日
```

`q_base`は全国宅配便取扱個数の人口換算原単位であり、個人宅向けの1人当たり配送需要、注文率、配送先数または配送停止回数ではない。

### 3.3 メッシュ別合成需要

対象日数`T`について、メッシュ別期待需要を次とする。

```text
D_m_expected = N_m * q_base * T
```

整数需要`D_m`は、区全体の需要を先に四捨五入し、メッシュへ最大剰余法で割り当てる。同率時は`KEY_CODE`昇順とする。

```text
D_ota = round(736652 * q_base * T)
sum_m(D_m) = D_ota
```

`T=1`の初期基準では次となる。

```text
期待需要 = 82,023.204937269... 宅配便個数相当／日
整数需要 = 82,023 宅配便個数相当／日
```

## 4. 未最適化基準の計算フロー

1. 公開原本のSHA-256と表・列・基準日を検証する。
2. 500mメッシュコードからJGD2011のメッシュ形状を再構成する。
3. N03大田区境界との交差率を求め、2020年人口分布から2024年推定メッシュ人口`N_m`を作る。
4. `q_base`と`T`からメッシュ別合成需要`D_m`を作る。
5. `D_m`を共通の集約配送点へ割り当てる。宅配便個数相当を1個1停止へ変換しない。
6. 共通実験設定から拠点、車両、積載量、稼働時間、EV条件を読み込む。
7. 各集約配送要求へ、凍結済み要求IDと入力manifest SHA-256からSHA-256優先キーを作る。
8. 優先キー昇順の要求列を保持したまま、固定車両ID昇順へ容量内で逐次割当てする。距離、時間、交通、将来のSUMO結果または目的関数を使って順序を変更しない。
9. `depot -> fixed order -> depot`を道路経路化し、古典最適化・QAOAと同一のSUMO環境で走行する。
10. 期限、容量、SOC、終端条件を満たしたメッシュ別配送完了量`Y_m,baseline`を集計する。
11. 需要充足人口相当`P_eq_baseline`を主計算で算出する。

## 5. 未最適化基準の固定順序

正式名は`fixed_hash_no_reordering`とする。要求`i`の優先キーは次とする。

```text
priority_i = SHA256(
    baseline_version || demand_manifest_sha256 || request_id
)
```

ハッシュ値のバイト列昇順、同値時は`request_id`昇順とする。任意の乱数seed、座標順、メッシュコード順、近傍距離、所要時間は使用しない。これにより、地理的に並ぶメッシュコードが偶然効率的な走査順を作ることと、結果を見てseedを選ぶことを避ける。

この方式にも車両への逐次割当てという研究上の規則があるため「ルールなし」とは表現しない。実運用比較が必要になった場合は、実在事業者の根拠が得られた別比較器を追加し、この基準を上書きしない。

## 6. 主計算

人口メッシュ`m`、解法`s`について、公開人口を`N_m`、人口換算原単位を`q_m`、対象日数を`T`、期限内に配送を完了した宅配便個数相当量を`Y_ms`とする。

```text
P_eq(s) = sum_m min(N_m, Y_ms / (q_m * T))
```

初期基準では`q_m = q_base`とする。未最適化、古典最適化、Aer QAOAは同じ`N_m`、`q_m`、`T`、整数需要`D_m`、集約配送点、車両、交通・環境条件、SUMO seed群を使用する。

```text
Delta_classical = P_eq_classical - P_eq_baseline
Delta_qaoa      = P_eq_qaoa      - P_eq_baseline
Gap_qaoa        = P_eq_qaoa      - P_eq_classical
```

`P_eq`は需要充足人口相当であり、実際に配送を受けた人数ではない。

## 7. 現時点で計算できる範囲

公開原本の取得と区全体の`q_base`、期待需要、整数需要の再計算は完了している。メッシュ別`N_m`と`D_m`は、500mメッシュ加工コードと境界交差テストの実装後に生成する。

`P_eq_baseline`は、集約配送点、拠点、車両、稼働時間、配送完了判定およびSUMO道路網が未固定のため、現時点では計算しない。これらを公開データの観測値であるかのように補わない。

## 8. 使用しない直接変換

- 東京都市圏物資流動調査の「回／世帯・週」を`q_base`へ直接変換しない。
- 「回／世帯・週」と「個／人・日」の比から東京補正係数を作らない。
- 全国宅配便個数を実顧客数、実配送先数または配送停止回数へ直接変換しない。
- JARTIC交通量を配送需要へ変換しない。JARTICはSUMO交通環境の較正・検証に使用する。
