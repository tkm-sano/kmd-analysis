## この文書の目的

本研究は、オープンストリートマップ（オープンストリートマップ）を基礎道路データとして、交通シミュレータースーモで使用する
大田区の道路網を構築するものである。ただし、オープンストリートマップの道路情報をそのままスーモへコピーすることは
できない。道路によって、方向別車線数、速度、車種別通行権限、右左折関係などが欠損していたり、
複数の解釈が可能であったりするためである。

Phase 12までに確認したのは、固定した入力と実行環境から道路属性処理を2回独立に実行したとき、
同じ成果物を再現できることである。これは処理の決定性と再現性が確認できたという意味であり、
すべての道路属性が解決済みという意味ではない。Phase 12の正式基準には、現状の情報・規則・
実装では正式値を決定できない阻害要因が108,189件保存されている。

Phase 13では、この108,189件を道路ごとに手修正しない。多数の阻害要因を発生させている少数の
共通原因を見つけ、判断根拠、登録簿、データ構造、実装を修正する。修正は小型検証用データ、独立正解判定器、
全道路stage 試験、回帰試験で検証し、最終的に全道路を2回独立に再実行する。Phase 14では、
その道路属性成果物をスーモ変換へ渡してよい品質かを正式判定する。

Phase 14に合格した後も道路網は完成ではない。承認済み属性をスーモのノード、道路区間、車線、接続へ
変換し、構造・通行権限・接続・信号・実走行を検証したうえで、別の交通シミュレーターの道路網 Integration
Acceptanceを行う。その後、一般交通を較正し、較正に使わなかった観測で独立検証を行い、
初めて配送手法の比較へ進む。本書は、この一連の過程について、現在地、理由、実作業、成果物、
完了条件を第三者が追跡できるようにする実行計画書兼作業記録である。

<a id="21-blockerとexclusionの違い"></a>

## 2.1 阻害要因と除外の違い

`blocker`は、本来は研究対象に含まれる記録であるが、現在の情報、登録規則、または実装だけでは
正式値を決定できない状態である。例えば、研究対象道路に`lanes=2`としか書かれておらず、双方向の
配分根拠がない場合、その道路を消すのではなく、方向別車線の阻害要因として保持する。

`exclusion`は、研究設計上、そもそも今回の対象外であることを、事前定義された規則と正本 根拠
から判断した状態である。除外は失敗を隠す手段ではなく、研究対象母集団の境界を説明する判断である。
道路識別子、除外理由、登録規則識別子、根拠、承認者、日付、母集団への影響を追跡できなければならない。

したがって、次の理由では正式除外してはならない。

- 属性が欠損しているから
- 実装が難しいから
- 阻害要因件数が多いから
- 調査時間が足りないから
- Phase 14へ早く進みたいから

つまり、`unresolved`または`blocker`を除外へ移して見かけの件数を減らすことは禁止である。
阻害要因は根拠を得て解決するか、必要な証拠を明示したまま保持する。除外へ移せるのは、研究対象外で
あることを独立した正本 根拠と登録済み規則で証明できる場合だけである。

## 3. 根本原因修正の共通反復手順

### この手順の目的

Phase 13の基本方針は、108,189件を人手で個別修正することではなく、108,189件を発生させている
少数の共通原因を再実行可能な規則として直すことである。同じ原因から生じた道路を一括して正しく
処理できれば、修正理由と影響範囲を説明でき、同じ入力から同じ結果を再生成できる。

実作業では、まず実際に停止した道路とオープンストリートマップタグを見る。次に、なぜ停止したかを分類し、オープンストリートマップ仕様、
法令、承認済み研究方針などの判断根拠を調べる。その人間の判断を判断 記録と登録簿へ
機械可読な規則として移し、小型検証用データと正式運用-independent 正解判定器で確認する。その後、全道路へ
stage 試験を行い、修正前後をstable 識別子で比較し、最後に全回帰試験を実行する。判断、コマンド、
終了コード、記録、ハッシュ値を記録することで、「たまたま動いた」のではなく、なぜ変更して何が変わったかを
再検証できるようにする。

各最上位 causeについて、次の順序を変更しない。

- [ ] 対象阻害要因 識別子を固定一覧から抽出する。
- [ ] 実際のオープンストリートマップタグ・方向・車線・車種・文脈・出典・来歴を一覧化する。
- [ ] 根本原因を再確認し、件数だけを理由に判断しない。
- [ ] 正本 根拠を確認する。
- [ ] 判断 記録を新しい版付きファイルとして作成する。
- [ ] 登録簿または判断 tableを更新する。
- [ ] 必要ならジェイソン形式 データ構造を更新する。
- [ ] 意味上の invariantと追跡可能性を更新する。
- [ ] 小型検証用データを追加する。
- [ ] 正式運用実装から独立した正解判定器を追加する。
- [ ] 属性解決器実装を更新する。登録簿駆動で変更不要な場合は理由を記録する。
- [ ] 検証用データ 試験を実行する。
- [ ] focused integration 試験を実行する。
- [ ] 母集団全体 stage 試験を新規出力へ実行する。
- [ ] 修正前後の阻害要因 識別子差分レポートを生成する。
- [ ] 固定analysis コンテナーで全回帰を実行する。
- [ ] コマンド、終了コード、ログ、ログSHA-256、成果物SHA-256をPhase 13実行履歴へ追記する。

各反復の完了条件:

- 判断理由がオープンストリートマップ仕様、法令、承認済み研究方針または登録証拠へ結び付く。
- 対象外記録が変化していない、または全変化が説明されている。
- 新規の説明不能阻害要因が0件である。

## 4. TODO A: `psv`・`motorcar`・`horse`の車種意味を確定する

### この工程の目的

オープンストリートマップの車種表現を、本研究で管理するスーモ車種へ一意かつ根拠付きで対応させる工程である。オープンストリートマップに
`motorcar=yes`と書かれていても、それが本研究の`passenger`、`taxi`、`delivery`のどこまでを
含むかを決めなければ、配送車両の通行可否を正式に判断できない。

### 現在何が問題なのか

最初の車両 概念体系修正後のstage 試験では、`horse` 130件、`motorcar` 154件、`psv` 16件が
未登録の車種領域として残った。単に既存車種へ広く割り当てると、本来通れない配送車両を許可する
可能性がある。逆に空集合へすると、本来適用すべき通行規則を失う可能性がある。

### 実際に何をするのか

例えば`motorcar=yes`を持つ道路地物について、同じ道路地物の`access`、`vehicle`、`goods`等を確認し、オープンストリートマップ仕様と
本研究の管理された 車両定義から対象車種集合を決める。判断を登録簿へ登録し、小型検証用データで
`delivery`への効果を確認した後、全道路へ適用して阻害要因差分を見る。

```text
OSMに motorcar=yes がある
  → motorcarがpassenger / taxi / deliveryのどこまでを表すか確認する
  → OSM仕様と研究車両定義を根拠に決定する
  → Registryへ登録する
  → fixtureと独立oracleで確認する
  → 全道路へ適用する
  → blocker ID差分を確認する
```

### この工程が終わると何が分かるか

オープンストリートマップの`psv`、`motorcar`、`horse`表現が、本研究のどの車種へ影響するか、または影響しないかを規則識別子と
根拠から説明できる。これにより、車種概念体系不足と、本当に別の接続根拠が不足している道路を
区別できる。

## 16. オープンストリートマップ属性からスーモ標準の拡張マークアップ形式への変換

### この工程の目的

Phase 14で承認した道路属性を、スーモが読み込めるノード、道路区間、車線、接続等の入力形式へ変換する工程で
ある。オープンストリートマップ 道路地物は一つの道路形状を表すが、スーモでは走行方向、区間、車線、接続を別の要素として表すため、
単純コピーではなく、承認済みの解釈結果を明示的に投影する必要がある。

### 現在何が問題なのか

Phase 14が未実行であるため、正式 スーモ 構築 入力はまだ承認・固定されていない。また、現在の成果物を
スーモ形式へ変換しても、それを正式道路網として使用する権限はない。

### 実際に何をするのか

関係は次のとおりである。

```text
OSM Way
  → Directed Segment（OSM Wayを方向と区間へ分けた研究側record）
  → SUMO Edge（SUMO上の一方向道路区間）
  → SUMO Lane（Edge内の個別車線）
```

オープンストリートマップにある方向、車線、速度、接続等を研究側の承認済み規則で解釈し、その確定結果からスーモ plain 拡張マークアップ形式を
生成する。同時に、スーモ 車線から方向付き区間、元オープンストリートマップ 道路地物へ逆引きできるlineageを保存する。

### この工程が終わると何が分かるか

## 17. 通行許可の具体化処理

### この工程の目的

Phase 13〜14で確定した車種別通行判断を、スーモが実際に強制できる`allow/disallow`へ変換する工程である。
属性解決器が「配送はこの車線を通行できる」と判断しただけでは、スーモはその判断を知らない。
通行許可の具体化処理が通行許可 期待値を車線と接続へ書き込むことで、simulation実行時の
経路探索と走行制限へ反映される。

### 現在何が問題なのか

正式 通行許可 期待値とスーモ 拡張マークアップ形式の間には、車線 位置の並び、スーモ 車線 索引、接続、
全車種禁止等の変換規則が必要である。この投影が不完全だと、属性側で拒否した車両がスーモでは通れたり、
許可した車両が経路を作れなかったりする。

### 実際に何をするのか

通行許可 期待値を読み、オープンストリートマップ 車線 位置をスーモ 車線 索引へ対応させ、車線と接続の
`allow/disallow`を生成する。全車線禁止道路区間など具体化できないものは黙って消さず、欠落 成果物一覧へ
理由を残す。最終 `net.xml`を人間が直接編集すると、正式入力と生成結果の関係が失われ再現できないため、
修正は管理対象の 入力、登録簿、または変換実装へ行い、再度`netconvert`する。

### この工程が終わると何が分かるか

属性成果物で決めた車種別通行許可と、スーモ lane/connectionに書かれた通行許可が完全に対応する。
配送車両がなぜ通れる、または通れないかをオープンストリートマップタグからスーモ 拡張マークアップ形式まで追跡できる。

- [ ] 次を確認する。

## 18. 交差点・接続・信号制御レビュー

## 21. スーモ 実行時間走行検証

### この工程の目的

道路ファイルを生成・負荷できることと、車両が意図どおり走行できることは別である。この工程では、
代表的な出発地・目的地（出発地・到着地）間で実車両を走らせ、静的な拡張マークアップ形式検査だけでは見つけにくい接続・通行許可・
信号の問題を確認する。

### 現在何が問題なのか

道路網候補は未生成であり、経路探索、走行、信号通過の実行時間検証も未実施である。拡張マークアップ形式が妥当でも、
車線 接続が途切れて経路を作れない、通行許可が誤って禁止道路を許可する、信号リンクが接続と
対応しない等の問題があり得る。

### 実際に何をするのか

代表出発地・到着地と期待結果を事前固定して配送車両を走らせる。確認項目の意味は次のとおりである。

- 一方通行: 許可された方向だけを走ること。
- 接続制限: `delivery`が禁止車線へ入らず、許可車線は利用できること。
- 車線 接続: 進入車線から正しい退出車線へ連続して移動できること。
- 右左折制限: 禁止された右左折・U-右左折を経路が使用しないこと。
- 信号: 車両が対応する信号リンクと段階に従って停止・進行すること。
- 経路 不具合: 到達可能な代表出発地・到着地で経路生成に失敗しないこと。
- teleport: 接続不良や長時間停止によりスーモが車両を強制移動していないこと。

### この工程が終わると何が分かるか

配送車両が代表的な道路条件で、方向、通行許可、接続、右左折、信号を守って走行できることが
確認できる。失敗した場合は、どの構築または確認工程へ戻るべきかを特定できる。

- [ ] 代表出発地・到着地とexpected 正解判定器を事前固定する。
- [ ] 次の想定条件を含める。
  - 幹線道路のみ
  - 住宅道路を含む
  - 一方通行を含む
  - 通行規制付近
  - 信号交差点

- [ ] 禁止道路を通行しないことを確認する。
- [ ] 一方通行遵守を確認する。
- [ ] 接続が正常であることを確認する。
- [ ] 信号link/phaseが正常であることを確認する。
