- ディレクトリ構成
- Markdown / CSV / YAML / Python スクリプト
- デモ入力と既存デモ出力
- 実行可否と依存関係

補足:
`.docx` ファイルは存在確認のみを行い、本文解析は今回の調査対象外とした。

## 2. エグゼクティブサマリ

`02-sample` は単なるコード置き場ではなく、研究計画、データ取得台帳、入力テンプレート、デモデータ、実行スクリプト、成果物見本をひとまとめにした再現用パッケージとして整理されている。特に `README.md`、`docs/`、`sources/`、`config/` の整備が丁寧で、研究作業の上流から下流までを見通しやすい。

このフォルダの中心的な役割は、量子計算が材料探索を効率化したと仮定したとき、その技術的改善を都市への就業流入の変化へ接続して評価することである。言い換えると、量子計算そのものの性能評価だけをする環境ではなく、材料科学の技術ショックを都市・交通・就業流動の変化へ翻訳する学際的な分析環境である。

この環境で可能な研究は、主に次の種類である。

- 文献レビューに基づく量子計算の材料探索改善度の整理
- 産業群別の軽量化率・燃費改善率シナリオの構築
- 一般化交通費を説明変数とした都市就業流入の PPML 重力モデル推定
- 技術改善シナリオごとの都市別・産業群別反実仮想比較
- 公的統計と文献を接続した再現可能な研究パッケージの整備

一方で、現行端末環境ではデモ実行を再現できなかった。`validate_inputs.py` による入力検証は正常終了したが、`run_analysis_environment.py` 実行時に `statsmodels` の import で停止した。確認できたローカル環境は `pandas 3.0.2`、`statsmodels 0.14.0` であり、`requirements.txt` にバージョン固定がないことが実行再現性の弱点になっている。

結論として、`02-sample` は「研究パッケージとしての設計」は良好だが、「新しい環境でそのまま再実行できる状態」にはあと一歩である。

## 4. このフォルダは何のための環境か

`02-sample` は、量子計算による材料探索の改善を、都市経済的なアウトカムである「都市への就業流入」に接続して検討するための統合研究フォルダである。対象は純粋なアルゴリズム性能比較ではなく、以下の二段階をつないだ評価にある。

1. 上流段階
量子計算が古典計算に比べて、材料探索の計算コスト、探索時間、有効候補生成効率をどれだけ改善しうるかを、文献レビューから整理する。

2. 下流段階
その改善が材料の軽量化率や燃費・電費改善率を通じて一般化交通費を変化させ、その結果として都市への就業流入がどの程度変わるかを、重力モデルで推定する。

したがって、このフォルダは「量子計算の社会経済的波及効果を、材料・交通・都市就業の連鎖として評価する研究環境」と位置付けられる。

## 5. この環境で可能な研究

本環境で実施可能、または今後実データを入れることで実施可能になる研究は、次のように整理できる。

### 5.1 文献整理型の研究

- 量子計算が有効な材料探索問題類型の整理
- 問題類型ごとの古典条件と量子条件の比較表作成
- 一次文献、レビュー、専門家判断を分けた証拠統合
- 技術仮定の悲観・基準・楽観シナリオ設計

### 5.2 工学翻訳型の研究

- 材料探索改善度を産業群別の軽量化率へ翻訳する研究
- 軽量化率から燃費・電費改善率への換算ルールの比較
- 翻訳パラメータの感度分析

### 5.3 都市・交通経済型の研究

- 一般化交通費弾力性の産業群別推定
- 自動車依存度が費用感応度をどう変えるかの推定
- 都市別・産業群別の就業流入に対する反実仮想比較
- 交通費構成要素の変更が都市流入に与える差の評価

### 5.4 学際統合型の研究

- 材料科学の技術改善を都市経済モデルへ接続する実証設計
- 公的統計と論文レビューを接続した再現可能パッケージの作成
- 将来の政策議論に向けた「技術進歩が地域分布に与える影響」の予備的評価

逆に、このフォルダだけで直接できることには限界もある。例えば、量子アルゴリズムそのもののベンチマーク実験、実験室レベルの材料特性測定、動学的な長期予測、個票データを用いた因果識別は、この環境の主目的ではない。

## 6. 実装の中身

### 6.1 実行フロー

実行の中心は `src/run_quantum_commuting_model.py` で、処理は大きく 3 段階で構成されている。

1. `benchmark_evidence` から古典条件と量子条件の比較表を生成する。
2. 比較表を産業群別の改善度に集約し、軽量化率と効率改善率へ翻訳する。
3. `od_flow` に対して PPML 重力モデルを当て、一般化交通費の変化を反実仮想として流入就業者数へ反映する。

`src/run_analysis_environment.py` は、この本体を標準ディレクトリ構成で呼び出すラッパーである。`src/validate_inputs.py` はファイル存在、必須列、空データの有無を点検する。

### 6.2 デモデータの規模

デモ入力は次の規模だった。

- `benchmark_evidence_demo.csv`: 30 行 15 列
- `od_flow_demo.csv`: 336 行 9 列
- `translation_parameters_demo.csv`: 3 行 8 列
- `model_controls.csv`: 5 行 3 列

既存のデモ出力は次の規模だった。

- `benchmark_comparison.csv`: 6 行 18 列
- `industry_translation.csv`: 9 行 6 列
- `coefficient_estimates.csv`: 3 行 5 列
- `results_by_od.csv`: 1008 行 22 列
- `results_by_city_industry.csv`: 63 行 7 列

### 6.3 デモ出力から読めること

既存の `run_summary.txt` と集計結果から、基準シナリオでは金属素材群で相対変化率が大きく出やすい。都市別の差分合計は東京、大阪、名古屋の順に大きかった。

推定係数の例:

- 金属素材群: 平均自動車依存度での一般化交通費弾力性 `-0.982`
- 化学・高分子素材群: `-0.731`
- 無機素材群: `-0.616`

このため、デモ設計上は「材料探索改善が交通費を通じて就業流入にわずかに効く」という方向性を確認する用途に向いている。

## 7. 良い点

- 文書、データ台帳、テンプレート、コード、デモ出力が一式そろっている。
- `README.md` だけで作業全体像を追える。
- 上流の文献抽出表と下流のモデル投入表が分けられており、研究実務と整合的である。
- `data_management_plan.md` や `review_protocol_template.md` があり、再現性だけでなく運用統制も意識されている。
- デモ出力が同梱されているため、完全実行できない環境でも期待成果物の形を把握できる。

## 8. 課題とリスク

### 8.1 実行環境の再現性が弱い

今回の環境では、以下のエラーで本体実行が停止した。

```text
TypeError: deprecate_kwarg() missing 1 required positional argument: 'new_arg_name'
```

確認できたローカル環境:

- `pandas 3.0.2`
- `statsmodels 0.14.0`

`requirements.txt` は `numpy`, `pandas`, `statsmodels`, `pyyaml` のみで、互換バージョンが固定されていない。このため、別環境で再現する際に依存関係の不整合が起きやすい。

### 8.2 検証は最小限で、実務上の異常値までは防げない

`validate_inputs.py` は以下しか見ていない。

- 必須ファイルの存在
- 必須列の存在
- 行数 0 でないこと

そのため、次のような問題は実行前に検出できない。

- 古典条件と量子条件の対応漏れ
- `cost_index` や `time_hours` のゼロ・負値
- 産業群と翻訳パラメータの不整合
- シナリオ設定値の欠落や不自然な範囲

### 8.3 一部設定ファイルが実行時には使われていない

`config/project_settings.yaml`、`config/scenario_settings.csv`、`config/city_definitions.csv`、`config/problem_class_definitions.csv` は文書的価値が高いが、今回確認した `src/` の実行コードからは参照されていない。

また、`model_controls.csv` の `scenario_default` も読み込まれるが、実行時には `low/base/high` を固定で回しており、挙動に反映されていない。設定ファイルと実行ロジックが部分的に分離している点は注意が必要である。

### 8.4 実データ導入はこれから

`data/actual_input/` は空であり、現状はデモ中心の配布物である。したがって、研究パッケージとしてはよくできているが、実証分析そのものはまだ入力整備待ちの段階と判断できる。

## 9. 総合評価

`02-sample` は、研究計画ベースの実証分析環境としてはかなり見通しが良い。特に、上流の文献レビューから下流の反実仮想推定までを一つのフォルダ構成に落とし込んでいる点は強い。

ただし、現時点では「説明可能な分析環境」としては完成度が高い一方で、「クリーンな環境に入れて即実行できる再現パッケージ」としては未完成である。今後は依存関係固定、設定ファイルの実行接続、入力検証の強化を行うと、研究用アーカイブとして一段強くなる。

## 10. 優先度付き改善提案

1. `requirements.txt` をバージョン固定形式にし、動作確認済みの Python / pandas / statsmodels 組み合わせを明記する。
2. `validate_inputs.py` に値域チェックとペア整合チェックを追加する。
3. `config/scenario_settings.csv` と `project_settings.yaml` を実行コードから参照し、設定と実行の二重管理を減らす。
4. 実行成功時の環境構築手順を `README.md` に追記する。
5. 実データ投入後に `actual_run` のサンプル出力仕様を別紙化する。
