## 2. 需要の計数と生成契約

顧客ID（配送を受ける主体）、注文ID（取引）、PE（未校正の荷物相当量）、stop ID（実際の訪問地点）を別に保持する。PEを荷物実個数・重量・顧客数へ換算しない。複数顧客を同じ建物・停車位置へまとめるならcustomer→order→stopの対応表と集約理由を保存する。

元計画の表・図は「顧客」と記載する一方、約100訪問／台・102秒／訪問を用いる。旧39,956は同一建物で集約した地点であり、個人顧客ではない。Nが顧客数か一意の訪問地点数かは**H01**。Nを黙ってstop数へ置換しない。H01解決までは地理需要の生成と本実験を停止し、一般的な整数配分の契約試験だけを許容する。

地域gの採択人口をP_gとして、w_g=P_g/ΣP_k、理想配分a_g=N×w_gとする。

1. b_g=⌊a_g⌋を配る。
2. 残りR=N−Σb_gを、a_g−b_gの降順に1ずつ配る。同率はregion_idの文字列昇順。
3. N_g≥0、ΣN_g=N、人口0の区画はN_g=0を検査する。負・非有限人口、空表、人口合計0は入力エラー。

`src/kmd_toc/contracts.py:allocate_customers` はこの算術だけを実装する。有限小数を有理数として扱い、浮動小数誤差による配分合計のずれを防ぐ。人口の正当性や区画対応を検証した関数ではない。

人口台帳はsource URL、発行主体、統計基準日、対象人口の定義、表・列・セル、取得日、ローカルパス、SHA256を必須とする。区画台帳はregion_id、境界ファイル・SHA256、CRS、境界年次、対象地域への被覆・重複、旧56区画との対応を必須とする。人口・境界の採択はH02。旧2020年メッシュを2024年人口へ補正した方式を自動採用しない。

各区画の住宅候補からの抽出規則、復元／非復元、seed、安定した行順、住宅用途フィルタを事前登録する。候補不足はHOLDとし、他区画への再配分や候補の架空追加で合計を合わせない。人口比でNを配分することからPE総量は導けない。PEの与え方はH03、住宅と道路の接続・仮想拠点入口・全必要ODはH04。

## 3. 配送・積込の連動モデル

車両v、便r∈{1,2}、顧客／地点i、バースbを識別する。決定対象は顧客の車両・便への一意割当、各便の訪問順、積込順序、バース割当・積込開始時刻。帰着時刻と第2便の積込可能時刻はこれらに整合する従属値である。

- 各便は拠点から出発し、割当先のサービスを終えて同じ拠点へ帰着する。全対象をちょうど1回扱い、未配達を省いて距離改善としない。
- 道路距離d_ij［m］と道路所要時間t_ij［s］は別の有向行列で保持する。距離を時間の代用にしない。現段階は共通の静的ODを想定し、実交通の再現は主張しない。
- 積込開始L_vr、所要時間ℓ_vr、出発E_vr=L_vr+ℓ_vr。帰着R_vr=E_vr+Σt_ij+Σs_iとする。任意の途中待機は採用しない。必要な休憩等を追加する場合は別途明示して全条件に共通化する。
- 第1便の積込可能時刻A_v1は共通運行条件。第2便はA_v2=R_v1+p_v（帰着後準備時間）。L_vr≥A_vr。第2便を別車両へ移して接続を切らない。
- バース使用区間は半開区間[L_vr,L_vr+ℓ_vr)。同一バースで重複不可、同時使用数はケースのバース数以下。同時刻の終了と開始は接続可。
- 各便のΣq_i≤Q_vr、最終帰着≤採択勤務終了時刻等を全条件共通で独立検査する。Q、q、s、ℓ、p、勤務終了時刻は未採択値を補完しない。

帰着後準備は積込とは別の時間であり、準備中のバース占有は前提にしない。占有が必要ならH05で明示する。第1便の積込可能時刻を積込開始に合わせて書き換えたり、道路上で任意に待ってWを減らしたりしない。拠点で積込可能後に計画的に待つ時間もWへ含める。既存の単一便帰庫期限32,400秒を新しい2便の勤務時間として流用しない。

## 5. 指標・時間境界・保存形式

|指標|定義|単位|
|---|---|---|
|D|全車両・全便、拠点往復を含むΣd_ij/1000|km|
|W1|第1便のΣ(L_v1−A_v1)/60|min|
|W2|第2便のΣ(L_v2−A_v2)/60|min|
|W|W1+W2|min|
|T|入力準備開始から、評価する採用計画が可行性検査を通り利用可能になるまでの経過時間|s|
|first_feasible_T|同じ起点から最初の可行計画が利用可能になるまでの経過時間|s|

Tは単調時計で測る。採用計画を後から変更したら、その変更後の利用可能時点へTも更新する。最初の可行解の時刻と、探索後のD・Wを組み合わせない。共通入力ファイルの事前作成・道路行列構築時間は別途台帳化し、比較時に共有する境界を全条件で揃える。方法固有の入力変換、初期計画の作成、前処理、パラメータ調整、反復、計算、復号、独立可行性検査、統合はTに含む。タイミング内訳の重複加算でwall時間を作らない。

最初の可行解取得後に候補が改善しなかった場合、採用計画そのものの利用可能時刻と、探索終了までの総経過時間を別々に保存する。探索の停止条件・実消費時間を隠さない。上限終了時の採用解を比較するなら、その採用確定時点をTとする規則をH07で揃える。

将来の保存契約（今回は結果CSVを生成しない）：

- `instances`：study/version、case、instance ID、入力seed、Nの意味、顧客・注文・PE・一意stop各総数、人口・境界・需要・ODのhash、設定hash。
- `customers`と`stops`：ID、region_id、建物ID、道路端点、q_PE、service_s、customer/order/stopの対応。不要な旧属性を持ち込まず新規の許可列だけを出力する。
- `plans`：plan ID、instance ID、手法、探索seed、status、可行性、D_km、W1_min、W2_min、W_min、T_s、first_feasible_T_s、総実行wall_s、採用規則、環境、入力hash。
- `trips`：plan/vehicle/trip ID、顧客順、バースID、積込可能・積込開始・積込終了・出発・帰着時刻［s］、q合計、距離［m］、道路秒、作業秒、準備秒。
- `timing`：方法固有の各処理の開始・終了、反復数、対象部分問題ID、計画利用可能・探索終了時刻。

statusは少なくとも`SUCCESS`、`TIMEOUT_WITH_FEASIBLE`、`NO_PLAN_WITHIN_BUDGET`、`INPUT_HOLD`、`ERROR`を区別する。未取得のD・W・Tはnull、打切り経過秒は別列。未取得を0距離・0待機・0秒へ変換せず、全試行を取得率の分母に残す。失敗と数学的不可行を混同しない。

同じinstance ID・入力hash・共通条件で対応させ、Δ=(候補−A)を各指標の元単位で報告する。相対差Δ/AはA=0ならnull。全3指標で悪化せず少なくとも1指標で改善なら優越、逆は被優越、同値、それ以外は比較不能とする。図の見た目だけで判定しない。`compare_objectives` は成功した対応計画の数値比較だけを実装し、対応確認・可行性検査の代替にはしない。
