# A全体の検証に必要な拠点データ：未送付の依頼仕様

本書とCSVは、取得項目と定義を具体化したものである。事業者への連絡・送信・取得を行ったものではない。個人名・電話番号は分析に不要である。位置情報を扱う場合は先方との合意・適切な匿名化方法を定める。任意の座標移動をしたデータから実道路距離を再現できるとは仮定しない。

## 必須の運行記録

[TARGET_TRIP_EVENTS_TEMPLATE.csv](TARGET_TRIP_EVENTS_TEMPLATE.csv)は1車両1便1行である。

- `observation_date/depot_id/vehicle_id/trip_no`：同一の日・拠点・車両・便を対応づける匿名IDである。
- `ready_s_JST`：その車両・貨物が積込可能となった時刻である。受付、到着、予約時刻、荷揃いのどれなのかを`ready_definition`に記す。待機を短く見せるために後から時刻を選ばない。
- `load_start_s_JST/load_end_s_JST`：積込作業の開始・終了である。単なる滞在や荷卸しを混ぜない。
- `departure_s_JST/return_s_JST`：その便のデポ発着である。日跨ぎは同じ午前0時基準で86400以上の秒も記録し、翌日0秒へ戻さない。
- `berth_id`：積込資源を識別する。予約や優先度、車内夜積み等はnotesへ記す。
- `driven_distance_m`：便の実走行距離である。デポ発着の含有、GPS/車載計/推計等の距離ソース、集荷を含むかを必ず記す。直線距離を実走行距離としない。

[TARGET_VISITS_TEMPLATE.csv](TARGET_VISITS_TEMPLATE.csv)は1回の訪問1行である。地点ID、実訪問順、担当区域、荷物数、到着・作業終了、位置/OD参照を対応させる。複数荷物・同じ建物・再訪問を区別し、訪問漏れや不在再配達を分析から黙って除外しない。

## 業務規則の記述

担当区域は固定か、変更は誰がいつ行うか、車両間の応援、荷物の到着時点、便の切り方、帰所/路上補充、訪問順を決める主体、時間指定・駐車・徒歩巡回、バースの予約/優先度/FCFSを確認する。特定の規則を前提にした誘導質問にしない。

## 計画時間：主にprogram Tを比較する場合は補足

[TARGET_PLANNING_WORKFLOW_TEMPLATE.csv](TARGET_PLANNING_WORKFLOW_TEMPLATE.csv)では、入力確定、対象地点・車両・便、出力、人数、同時作業、開始終了を定義する。wall時間と人時を区別する。個別ルート順序作成と全車両の割当・便・バース・検査を同一工程としない。

人手時間が取得できなくても、全手法のT_program比較自体は可能である。その場合に事業者の人手時間を代表したという解釈をしない。人手Tの数値を任意の規模比で作らない。

## 検証の流れ

1. 少数日の予備データで単位・定義・欠損・業務適合性・日間変動を確認する。
2. 校正用と独立検証用を日・区域等で分離し、合否の許容幅と必要な日数を事前設定する。根拠のない一律誤差率や固定日数を採らない。
3. 実績順を共通ODで再評価し、実測距離との差を道路モデル誤差として調べる。
4. 需要から生成するAの割当・順序・便・積込を実績と比較する。実績リストを読んだだけの計画をA本体の出力としない。
5. 共通の容量・サービス等が実態と不整合なら、研究条件全体の改訂案として報告する。Aだけを変更してB/C/Dとの順位を操作しない。

取得できない項目は未取得のまま残す。本書の準備は、拠点の代表性確認・実績取得が完了したことを意味しない。
