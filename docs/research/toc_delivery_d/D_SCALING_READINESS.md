# D：S1〜S3への接続準備判定

2026-11-10。Dの方式はHuang列生成法＋AOAである。[小規模報告](D_REFERENCE_IMPLEMENTATION_REPORT.md)、[縮小検証](D_PRICING_REDUCTION_STUDY.md)、[運行定式化](D_FORMULATION.md)を参照する。

## 2026-11-11追補：車両日列の小規模接続

外部コード監査後に、[車両日列の検証](D_VEHICLE_DAY_VALIDATION.md)と[最新の接続判定](D_VEHICLE_DAY_READINESS.md)を追加した。基本日列・古典主問題/価格付け・バース/勤務は人工有限格子でGO、AOA接続は改善列見逃しがあるためCONDITIONAL GO、S1〜S3はHOLDである。以下の2026-11-10本文にある「日列・バース未実装」は小規模部分について本追補で置き換える。研究規模での未実装・運行/ODのHOLDは解除しない。

## 1. 判定

小規模独立実装と研究規模の適用可否は分ける。S1〜S3の配送計画本実験は未実施であり、**研究規模はHOLDを維持する**。価格付けを12qubitへ縮小できることと、全4,000地点を運行条件どおり配送できることは同義ではない。

元の顧客単位one-hot表現では、50地点の便でも固定ブロック除去後2,550qubitが必要である。マクロ化は個々の顧客を固定順序の区間へまとめることで表現を制限しており、この下限を全域同値な符号化のまま破ったという意味ではない。

RQ・仮説・凍結需要・OD・車両/バース条件は変更しない。需要はS1/S2/S3それぞれ1,000/2,000/4,000地点、各1個である。車両は10/20/40台、バースは2/4/8、最大2便、顧客時間窓なしを維持する。

仮予算は、初期trip数≤2F、初期日列数≤F、各反復のdomain数≤2F、各domainの追加上限5列、反復上限20とした場合である。trip候補R≤2F+20×2F×5=202F、日列J≤F+20×2F×5=201Fとなる。日列5列への打切りは候補制限であり、全域価格付けの保証を持たない。初期日列の全配送可行性は未確認であり、この予算を研究実行可能性の根拠にしない。

同一容量Qが50未満なら、現在のN/F/最大2便では荷物総量の必要条件を満たさない。50を新しい容量として採用するという意味ではない。異種容量なら2ΣQ_v≥Nが必要であり、どちらも時間・バース制約の十分条件ではない。

距離/時間をfloat64で2枚保持するODの生配列は16(N+1)² bytesであり、約15.3/61.1/244.3 MiBとなる。新しいODは今回生成しない。主問題の顧客×日列部分を密float64で保存する仮の上限は8NJ bytes（上表のJなら約15.3/61.3/245.4 MiB）であり、占有行・solverメモリは追加である。実装は疎行列を前提とするが、U=ceil(H/Δ)と区間数が未確定のため総メモリを数値断定できない。

## 4. 運行制約へ接続するための条件

マクロを展開した順序付きtripは、個別顧客の距離/荷量/作業時間を元入力から検証する。次に物理車両vの1便又は2便へ組み合わせ、第1便帰着＋準備から第2便readyを計算する。複数の積込時刻候補を持つ日列jへD_j/W_j/占有b_ujを付け、顧客一度配送・各車1日列以下・バース同時使用B以下の主問題で選択する。

日列被約費用には顧客πだけでなく車両・バース・ε制約の双対を含める。小規模で検証した距離と顧客双対の保存だけでは、この価格付けを解いたことにはならない。最後に不適合ルートを捨てて未配送を残す処理は採用しない。

Q、配達作業時間、積込関数、初便ready、帰着後準備、勤務終了、時間精度を根拠付き共通入力として確定する。旧研究の独自容量・動力条件を流用しない。小さい人工問題の容量25又は4も研究車両の設定ではない。

## 5. 次段階へのゲート

1. 人工小問題で、マクロの候補更新・分割・向きの代替と、縮小により未取得となる負列をさらに検証する。
2. 小問題の日列主問題と完全な日列価格付けの古典oracleを実装し、2便・占有・勤務・Wを接続する。
3. 共通の道路/OD・容量・運行根拠・時間精度を採用し、凍結需要読込契約だけで接続する。
4. 長い初期可行便と、車両間再割当を許すマクロ候補の生成・完成を小規模から検証する。
5. Cにも同じ制約・時間割自由度・εprofile・計時境界を用意する。内部量子寄与の対照は同じCGの価格付けだけを古典化する。
6. 上記を満たした場合に限り、別途承認された次工程としてS1→S2→S3を実行する。今回は実行しない。

最終的な研究規模判定はHOLDである。縮小の小規模検証が成功しても、必要運行条件・全体可行性・探索範囲の問題を解消したことにはならない。
