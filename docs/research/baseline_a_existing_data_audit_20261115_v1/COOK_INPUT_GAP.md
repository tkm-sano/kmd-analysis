# Cook方式の大田区入力への適合確認

結論は**基礎的な地理・道路入力は利用可能であるが、著者方式の実績模倣部分を現状のまま大田区へ適用できるとは確認できない**である。これは入力と著者コードの静的照合の結果である。Cookのコンパイル・推論は今回実行していないため、実行性能・再現score・大田区の実績代表性を合格としていない。

## 使用版と必要項目

対象は[著者公開jpt-amz実装](https://github.com/heldstephan/jpt-amz)である。既存調査で保存・git blob照合された[build_TSPLIB.py](../baseline_a_literature_20261115_v1/sources/cook_build_TSPLIB.py.txt)、[apply script](../baseline_a_literature_20261115_v1/sources/cook_model_apply.sh.txt)、[build script](../baseline_a_literature_20261115_v1/sources/cook_model_build.sh.txt)を読んだ。[保存した版情報](../baseline_a_literature_20261115_v1/sources/GITHUB_SNAPSHOT_MANIFEST.json)を参照する。2021競技版コードと2022オンライン/2024巻号の改良論文版の完全対応は未確定である。

|必要情報・機能|現状|適用上の判断|
|---|---|---|
|配送地点ID・座標・拠点|S1〜S3に存在する。道路入力にも全件一致した|形式変換は可能と判断する。実停車位置・建物入口まで観測した情報ではない|
|地点間の有向移動時間|Route版ODが全組存在し、単位s・到達可能性・hashを確認した|著者のtravel_times形式への変換に必要な数値はある。ただし静的推計とAmazon履歴時間の意味の違いを残す|
|物理的な走行距離|Route版距離mも存在する|評価Dは必ずこの距離で計算する。Cookの時間重み・制約ペナルティを物理的距離へ加算しない|
|`station_code`|京浜拠点IDはある|識別子は作れるが、米国既知拠点と同じ学習済み区域選好を持つ証拠はない|
|実績の`zone_id`・階層的区域ID|事業者の区域はない。町丁目コードと建物属性はある|町丁目や座標分割をzoneへ置換することは追加仮定である。文字列を生成しても業務区域の同等性は成立しない|
|当該拠点の履歴訪問順・区域順|未取得である|`station_infos`・`superSets`等の大田区向け実績学習の根拠が不足する。A2やB/C/Dの提案順を実績として学習させない|
|荷物別時間窓・作業時間|現在は顧客時間窓なし、全地点120秒、各地点1配送単位である|作業時間は研究値として変換できる。著者コードの`-Windows`使用時は荷物別作業時間を足すため、1地点の120秒を二重計上しない。実時間窓を捏造しない|
|出発日時|合成日付と勤務・積込後の出発時刻を設定可能である|合成日・JSTと元コードUTCを明示的に変換する必要がある。実績日付として扱わない|
|車両割当・容量60・最大2便・バース|本研究の共通条件には存在する|著者方式の主対象は割当済みルートの訪問順であり、全車両・便・バースの生成は別モデルが必要である。既存A2へ順序だけ接続してもA全体の代表性は未解決である|

`build_TSPLIB.py`の571–572行は`station_code in stationInfos`の場合だけ区域順予測を呼び、604行以降も既知stationの`superSets`を参照する。未知拠点の識別子を付けるだけでは、この学習成分が同じように適用されるといえない。`-noZonePred`や`-noZone`はコードにあるが、欠損を避けるために無条件で有効化して、その結果を原方式の実績模倣として採択してはならない。

## 現在のデータから言える適合範囲

全規模で100地点/車両、容量60/便、最大2便である。容量総量だけから必要な便数は17/34/67便で、上限は20/40/80便である。この必要条件だけでは時間・バースの実行可能性は証明されない。また、S3の4,000地点全体をCookの単車両ルートと比べることは単位が異なる。将来の比較は自前の割当後の各便を単位に、元データの各ルートと対応づける必要がある。

道路上の別地点への最短距離が0となる地点はS1/S2/S3で2/2/14地点ある。これは座標の異なる建物が道路へ対応づけられた際の結果と整合するが、今回その全原因を特定したわけではない。著者コードが整数化する時間・距離や0重みでの挙動は、実行試験で確認する必要がある。建物を無断で統合したり、評価距離を正値へ補正したりしない。

住宅属性は全件結合できるが、既存CSVの`apartment`は建物候補の適合分類であり、実際の配達先世帯構成ではない。Amazon側と同じ定義の住宅型・入口・駐車・階移動・配達完了時間を今回取得できていないため、住宅構成が似ていると断定することもできない。

## 判定と次に必要な検証

|対象|判定|
|---|---|
|既存入力の地理・OD数値の利用可能性|PASS（今回確認したファイルと単位の範囲）|
|Cook著者実装への形式変換|CONDITIONAL（アダプタ・日時・サービス時間・0重みの実行検証が必要）|
|原方式の元問題での再現|未実施である|
|区域学習の大田区への移転|FAIL（当該区域・履歴が未取得であり、適合の必要証拠がない）|
|全体D/W/Tの実績代表性|FAIL（対象全体の適格な観測値が未取得）|

公開資料だけで進める次段階は、既存Amazonキャッシュを使い、原方式の少数ルート再現、未知拠点での学習成分の有無、公開zoneと自動区域との差を分離して検証することである。既採点32＋26ルート等は開発既知データであり、新たな独立検証標本として数え直さない。設定・予算・選択基準を固定してから未使用標本を採点する。

そこで元方式が動き、未知拠点でも有効だと分かっても、得られるのは海外データ上の移転性能である。京浜・大田区の実績代表性へ自動的に昇格させない。対象の区域履歴や適格な全体D/W/Tを公開資料から入手できなければ、国外実績に基づく暫定順序モデルという限定を残す。研究仮説の主比較への採択は保留である。
