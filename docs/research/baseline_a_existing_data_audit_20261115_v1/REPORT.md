# 既存データについての確認1〜3

2026-11-15に、①生成用と検証用のデータの区分、②現行需要の地域特性、③Cook方式に必要な入力の充足を確認した。結論は、**大田区の地理に基づく共通入力は既にあり、再取得・再生成する必要はない。一方、地理への適合だけでは配送実績を想定するAの代表性は確立しない**である。Cook方式の実績模倣に必要な当該拠点の区域・履歴と、対象全体D/W/Tの適格な実績値は依然未取得である。

## 1．何が生成用で、何が検証用か

[データ用途台帳](DATA_USAGE_LEDGER.md)に採用根拠と独立性を整理した。

- 国勢調査は合成世帯の人数構成へ使われている。保存された合成384,353世帯が引用する182行・724の行×人数階級を原表と再集計し、件数が一致した。
- 住宅・土地統計は合成住宅型の割当に使われている。大田区の住宅数の該当セルまで確認できた。ただし住宅数を世帯へ移転する仮定、確率の正規化、原生成器の不足は残る。
- 東京都市圏物資流動調査ss521は需要の相対強度へ使われている。週頻度の採用4セルと合成世帯構成による参照頻度を再計算できた。同じ表との一致は独立検証にはならない。
- PLATEAUは配送地点の位置・建物候補の基礎である。最終全地点と候補属性を一意に結合できた。上流の全変換コード・中間parquetは未回復であり、原本からの完全再生成を確認したわけではない。
- 家計消費状況調査と受取調査の追加PDF/表は取得済みであるが、存在だけで現行需要への採用や未使用の独立検証資料とは判定しない。支出額、受取回数、配送地点数、荷物数を同じ量として換算しない。
- Amazon実績は大田区需要の生成には使っていないが、既存の訪問順校正32ルート・別拠点検証26ルート等には使用済みである。今後の方式選択では既知の開発データである。

したがって、既存データで上流加工の正確さと地理的な整合性を検査できる。しかし、それらを再度使って実務の車両割当・訪問順・便・バース・D/W/Tの独立検証が完了したとはいえない。

最近傍は当該規模の**他の抽出配送地点**に対して求めた。球面距離は半径6,371,008.8mのhaversine、凸包は平均緯度を基準とする局所正距円筒近似である。凸包は行政面積・住宅地面積ではなく、非住宅地や水面を含み得る。上記密度は実際の大田区宅配密度ではなく、今回の抽出入力の密度である。`apartment`は保存された建物候補の適合分類であり、世帯比率や住戸数ではない。

凍結前の母集団は39,956合成建物停車、適格地点は34,912である。現在の整数配分は**元の建物停車数の町丁目別比率**に基づき、人口比例の直接抽出ではない。配分台帳は182区域を持つが、実際の抽出地点を持つのは各規模180区域である。S1⊂S2⊂S3の入れ子であり、独立需要3標本ではない。

上流PEから現行の1地点1単位へ変わるため、現在の容量60は建物訪問単位の制御容量として解釈する必要がある。S3の8,107 PEを4,000単位へ変えた入力で、実際の積載荷物数・住宅内複数配達の作業量が保存されたとはいえない。各地点120秒、積込1,800秒、最大2便、車両・バース数、勤務08–20時は現行v1.1の研究仮定であり、地域統計から校正された値ではない。

Route版の9配列すべてで保存hashが一致し、全組到達可能・有限非負値・ID順・次元が整合した。関東全域OSMのOSRM5.27.1静的carモデルであり、実走行GPSや混雑の観測ではない。旧Table版、旧SUMO道路網、過去単車両実験と混同していない。凍結当初のMANIFESTに残る道路・容量HOLDは履歴であり、後続Route版と現行v1.1の存在を打ち消す現在の判定とはしていない。

以上から、**大田区内の建物に基づき、京浜拠点からの道路移動を伴う合成比較ケース**とは説明できる。現実の一事業者がこの日量・密度・車両・便数で運行したケースとは説明できない。

## 3．Cook方式はこの条件で使えるか

[入力不足とコード上の条件](COOK_INPUT_GAP.md)を整理した。地点ID・座標・有向時間行列は揃い、サービス時間も研究値として変換可能である。既存需要を作り直す必要はない。

しかし、町丁目は事業者の配送区域と同義ではなく、大田区拠点の実績`zone_id`・区域階層・訪問順は未取得である。著者コードは拠点ごとの履歴区域順を利用する。未知拠点へ識別子を付けたり、町丁目をzoneと呼んだりして、その選好が移転されたとはいえない。既存建物属性を追加できることも、この不足を直接解消しない。

さらにCookの順序成分には、本研究の車両割当・2便・バースを生成する追加仕様が必要である。これは実装可能性と実績代表性を分けて判断すべき拡張である。今回は入力確認までであり、著者実装のコンパイル・実行・score再現を行ったとは報告しない。

|確認事項|今回の結論|
|---|---|
|生成用／検証用の区分|主要な生成接続と再使用不可の範囲を特定した。未回収の生成器や未確認の追加表の履歴は明示した|
|既存入力の地域特性|全S1〜S3を数値化し、原表・建物属性・Route行列との整合を確認した|
|Cookへの入力適合|地理・ODは利用可能、形式変換は条件付きである。当該拠点の実績区域学習の移転と実行動作は未検証である|
|大田区の実績代表性|FAILである。必要な区域・履歴・適格な全体D/W/Tの実績が不足している|
|研究仮説の主比較へのCook方式の採用|未採択である。現行Aについての既存の実装PASS／代表性FAILを変更しない|

次に進める作業は、新しい大田区需要の作成ではなく、既存キャッシュによるCook著者実装の少数ルート再現と、未知拠点・区域情報の欠損を分けた移転試験である。公開資料だけで対象実績を補えない場合は、大田区の実績代表という判定を保留したまま、適用範囲を限定した暫定モデルとして管理する。RQ・研究仮説を自動変更しない。

## 実施・再現・保全

開始HEADは`8605d5412f6af62229a83095c35ab04c8c7dd9b1`である。AGENTS.mdとREADME、既存変更を確認した。書込みはこの新規監査ディレクトリのみであり、既存アルゴリズム、需要・道路データ、README、RQ・仮説、設定を変更していない。

検査は需要生成・配送計画最適化を含まない記述統計である。1回90秒の上限を設け、成功2回の所要は約8.7秒・12.4秒であった。この時間は**監査の実行時間**であり、Aの計画作成時間Tではない。3種類の科学的JSONは2回ともバイト一致した。[再現照合](REPRODUCIBILITY.json)、[保全・実行環境](run03/VALIDATION.json)、[入力hash](run02/INPUT_HASHES.json)を保存した。保全対象94ファイル、読取入力34ファイルに変更はなかった。

最初のrun01は国勢調査の`-`記号の整数読込みで停止した。読取処理を修正してrun02/run03で検査を完了し、失敗出力も残した。元データの補正・置換・再生成は行っていない。

再実行は未使用の出力名で行う。

```bash
timeout 90s python -B \
  docs/research/baseline_a_existing_data_audit_20261115_v1/audit_existing_data.py \
  --output docs/research/baseline_a_existing_data_audit_20261115_v1/reproduce_new
```

使用環境はPython3.13.5、NumPy2.3.5、Linuxである。既存の凍結需要ローダを使用し、XLSXは標準ライブラリでセルを読み取る。出力先が存在すれば停止する。
